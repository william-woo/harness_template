# 측정 12 — 도구 호출 0건의 진짜 원인은 추론 예산이 아니라 **서버 컨텍스트 창**

> 대상: `gemma4:26b` / `gemma4:12b` / `qwen2.5:14b-instruct-q8_0`, Ollama 0.30.5 @ `172.16.10.217:11434`,
> OpenCode 1.16.2. 2026-11-04.
>
> 계기: ADR-021 결정 3(`limit` 등재·보정)을 활성 `localllm` 으로 복원한 뒤, 서버에 이미 있는
> `gemma4:26b` 로 스모크를 돌렸다. **`limit` 을 제대로 넣었는데도 도구 호출이 0건이었다.**

---

## 결론 먼저

| | 주장 | 상태 |
|---|---|---|
| ADR-021 결정 3 | 추론 모델은 `limit` 없이는 도구 호출이 0건이다 | **재현됨** (결과 1) |
| ADR-021 결정 3 | `limit` 을 등재하면 도구를 호출한다 | **반례 있음** — 필요하지만 충분하지 않다 (결과 2~4) |
| 새 사실 | 창을 정하는 건 서버이고 기본값은 4096 이다. OpenCode 의 도구 프리앰블은 혼자 ~12.7k 토큰이다 | **확인됨** (결과 3~5) |
| 새 사실 | 추론 모델만의 문제가 아니다 — qwen2.5:14b 도 4096 창에서 도구 인자 스키마를 어겼다 | **확인됨** (결과 6) |

**증상이 ADR-021 과 똑같아서 오진하기 쉽다.** 둘 다 `finish=length` + 도구 0건으로 끝난다.
구분 지점은 `usage` 다 — 예산 부족은 `completion_tokens` 가 한도까지 차고, 창 부족은
`prompt_tokens` 가 창−1 에서 멈추고 `completion_tokens` 가 1 이다.

---

## 결과 1 — 예산 축은 ADR-021 대로다 (재현)

`gemma4:26b`, 도구 1종, 프롬프트 동일, `max_tokens` 만 변화:

| max_tokens | finish | 도구 호출 | 출력 토큰 |
|---:|---|---:|---:|
| 64 | `length` | **0** | 64 |
| 512 | `tool_calls` | 1 (`read`) | 77 |
| 4096 | `tool_calls` | 1 (`read`) | 174 |

예산 하나만 바꿨는데 0 → 1 이다. ADR-021 결정 3 의 근거는 **그대로 유효**하다.
`1+1 은?` 같은 사소한 질문조차 64 예산에서는 `content: ''` 로 끝난다 — 답 1자(`2`)를
내는 데 추론이 ~90 토큰 들기 때문이다.

## 결과 2 — 그런데 하네스에서는 `limit` 을 넣어도 0건이었다

`opencode-setup.sh` 로 `limit: {context: 32768, output: 4096}` 을 등재하고 OpenCode 로
실행하면, gemma4:26b 는 **아무 출력도 도구 호출도 없이** 6~10초 만에 루프를 빠져나왔다.
`limit.output` 을 16384 로 올려도 같았다. `gemma4:12b` 도 같았다.

반면 같은 설정에서 `qwen2.5:14b` 는 도구를 호출했다 (실패했지만 — 결과 6).

## 결과 3 — 와이어를 보니 `limit.context` 는 **나가지 않는다**

OpenCode 와 Ollama 사이에 프록시를 끼워 실제 바이트를 기록했다.
OpenCode 가 보낸 요청의 생성 파라미터는 이게 전부다:

```json
{"model": "gemma4:26b", "max_tokens": 16384, "tool_choice": "auto",
 "stream": true, "stream_options": {"include_usage": true}}
```

`limit.output` → `max_tokens` 는 전달된다. **`limit.context` 는 와이어에 없다** — OpenCode
내부 컨텍스트 관리용이고, 서버에 창을 요구하지 않는다. 설정 파일만 보면 32768 로 보이지만
서버는 그 값을 듣지 못한다.

## 결과 4 — 창은 4096 이었고, 프롬프트가 거기서 잘렸다

같은 요청의 응답은 청크 2개로 끝났다:

```
delta {"role":"assistant","content":""}  finish_reason: "length"
usage {"prompt_tokens": 4095, "completion_tokens": 1, "total_tokens": 4096}
```

시스템 프롬프트 21,851자 + 도구 10종이 창을 다 먹고 출력 자리가 **1 토큰** 남았다.
`num_ctx` 를 요청에 넣어도 (최상위·`options` 양쪽) OpenAI 호환 엔드포인트는 **무시한다**.
창은 서버가 정한다.

## 결과 5 — 창만 키우자 통과했다 (요청 바이트 동일)

기존 태그를 그대로 두고 파생 태그를 만들었다 — 가중치를 공유하므로 디스크 추가 사용은 없고,
측정 01~09 의 대조군(qwen2.5)도 바뀌지 않는다:

```bash
curl $OLLAMA_HOST/api/create -d '{"model":"gemma4:26b-ctx32k","from":"gemma4:26b",
                                  "parameters":{"num_ctx":32768},"stream":false}'
```

기록해 둔 **같은 요청 바이트**를 두 태그로 재생한 결과:

| 모델 | finish | prompt / completion | 도구 호출 |
|---|---|---:|---|
| `gemma4:26b` (창 4096) | `length` | 4095 / 1 | **0** |
| `gemma4:26b-ctx32k` (창 32768) | `tool_calls` | 12749 / 100 | 1 (`glob`) |

OpenCode E2E 도 완주했다 — 4 라운드(제목 → `glob` → `read` → 최종 답), 19초,
답은 `widget-beta, widget-delta` 로 **정답**이다.

> 덧: OpenCode 1.16.2 의 `run` 은 비 TTY 에서 전사를 찍지 않고, TTY 에서도 **최종 답변
> 본문을 화면에 내지 않는다**. 위 답은 와이어에서 읽었다. 기능 실패가 아니라 표시 문제이지만,
> "도구는 부르는데 답이 없다" 로 오인하기 쉽다.

## 결과 6 — 추론 모델만의 문제가 아니다 (측정 04 결론 일부 정정)

`qwen2.5:14b` 를 같은 하네스로 돌리면 창 4096 에서 이렇게 실패한다:

```
✗ Read failed [path=inventory.txt]
  SchemaError(Missing key at ["filePath"])
```

인자 이름이 틀렸다. 이걸 "14B 의 도구 스키마 준수 한계" 로 읽기 쉽다 — 그런데
**같은 모델을 창 32768 로만 바꾸면 `filePath` 를 정확히 쓴다.** 도구 정의가 프롬프트
중간에서 잘려 나갔던 것이다.

따라서 측정 04 의 "단일역할 14B E2E 검증" 중 **도구 인자 품질에 관한 관찰은 창 조건을
명시하지 않은 채 기록됐다.** 모델 등급을 말할 때 창을 함께 적지 않으면, 모델의 한계와
환경의 절단을 구별할 수 없다.

## 하네스 반영

`opencode-setup.sh` 에 `[4/5] Ollama 서버 컨텍스트 창 점검` 을 넣었다:

- 모델에 `num_ctx` 가 박혀 있으면 `/api/show` 로 읽고, 없으면 1 토큰만 생성해 적재한 뒤
  `/api/ps` 의 `context_length` 로 **실측**한다 (서버 기본값은 API 로 조회할 길이 없다).
- 창이 필요치보다 작으면 **`=== 설정 완료 ===` 를 찍지 않고**, 파생 태그를 만드는
  `ollama create` 명령을 그대로 출력한다.
- 서버에 닿지 못해 **확인하지 못한** 경우도 완료로 적지 않는다 (`설정 완료 (서버 컨텍스트 미확인)`).
  이 분기는 실제로 필요했다 — 이 측정 도중 GPU 서버가 내려갔고, 그때 스크립트는
  창을 못 본 채 "설정 완료" 를 찍었다. **서버가 꺼져 있을 때 통과하는 점검은 점검이 아니다.**

회귀 테스트는 `tests/test_opencode_setup.py` 의 `ServerContextGateTest` 6건이다.
가짜 Ollama(`FakeOllama`)를 띄워 셸 스크립트를 **실제로 태운다** — 실서버를 쓰면 테스트가
GPU 박스의 전원 상태에 좌우된다. 6 동작 전부 변이로 사망을 확인했다.

> 변이 중 하나는 처음에 **살아남았다**: `추론 모델` 표시를 지워도 테스트가 통과했는데,
> 그 낱말이 마지막 배너의 다른 문장에도 있어서 `assertIn(stdout)` 이 엉뚱한 곳에
> 맞은 것이다. 해당 모델의 **점검 줄**을 보도록 고치고서야 죽었다.

## 남은 것

- `.217` 의 Ollama 는 0.30.5 다. `muse-glimmer:30b` 는 더 최신 런타임을 요구해 받지 못했다.
- 서버 전역 `OLLAMA_CONTEXT_LENGTH` 를 올리는 쪽이 파생 태그보다 간편하지만, 그러면
  측정 01~09 의 대조군 조건이 **한꺼번에** 바뀐다. 파생 태그는 기존 태그를 건드리지 않는다.
- 이 측정 중 서버에 `gemma4:26b-ctx32k` · `qwen2.5:14b-ctx32k` 두 태그를 추가했다.
  가중치 공유라 디스크 비용은 없지만, 정리하려면 사람이 결정한다 (삭제는 #3-A).
