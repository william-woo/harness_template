# 측정 11 — 호스트 성능 비교와 측정 도구의 숨은 가정 (F029)

> 대상: `localllm` 하네스를 **호스트만 바꿔** 비교 — 로컬 `qwen2.5:32b-instruct-q4_K_M`(OpenCode+Ollama)
> vs `claude-opus-5`(Claude Code CLI, `claude -p`). 무인 스위트·oracle·결정론 게이트는 동일.
> 시나리오 S01·S03·S05·S06·S09·S10 × 2라운드, 구간 교대. 2026-08-11~12.

## 설계 — 호출 지점 한 곳만 교체

`cycle_driver` 의 호스트 호출 지점(`_opencode_run`)에 분기를 넣어 `HARNESS_DRIVER_HOST=claude-code`
면 `claude -p --permission-mode bypassPermissions --model <m>` 로 위임한다. 나머지 파이프라인
(7층 결정론 게이트·정규화 4종·판정 기록 검증·유계 재작업)은 **두 호스트가 공유**한다.

`claude -p` 에는 opencode 의 `--agent` 대응물이 없으므로, 로컬 구간이 폴백으로 쓰는 **주입 모드**
(역할 브리프를 프롬프트 앞에 붙임)로 고정해 프롬프트 형태를 맞췄다.

## 결과 1 — 호스트 격차

| 지표 | 로컬 32B | Claude Opus 5 |
|---|:-:|:-:|
| PASS | 9/12 (75%) | **12/12 (100%)** |
| **완주율** (expect_exit=0 인 S01·S05·S06) | **4/6 (67%)** | **6/6 (100%)** |
| 거짓 결과 (ACCURACY) | 0 | 0 |
| 총 소요 | 19분 | 24분 |

시나리오별로 갈린 지점이 분명하다 — 로컬이 실패한 **S05(엣지케이스)·S06(다중파일 import)·S09(리팩토링)**
를 Claude 는 4/4 통과했고, 게이트 지배 시나리오(S03·S10)는 양쪽 다 안정적이었다.

> **지표 정정**: 초기 보고에서 완주율을 "33% vs 100%" 로 적었는데 **오류**였다. `expect_exit` 를
> 확인하면 완주가 정답인 시나리오는 S01·S05·S06 뿐이다 — S10(치팅 차단)은 exit 2 가 **정상**이고
> S03·S09 는 양쪽 다 허용이다. 정상 정지를 실패로 세면 격차가 두 배로 부풀려진다.

## 결과 2 — 하네스는 강한 호스트를 붙잡고 있지 않았다

32B 우회책(경로 지시·탭 금지·`bash cat` 강제·전체 재작성 강제 등 측정 08 산물)을 문장 단위로
제거한 lean 프롬프트로 Claude 를 다시 돌렸다.

| 구간 | PASS | 완주 | 총 소요 |
|---|:-:|:-:|:-:|
| Claude 원본 프롬프트 | 12/12 | 6/6 | 24분 |
| **Claude lean** (우회책 제거) | 12/12 | 6/6 | **31분** |

품질은 완전히 동일한데 **lean 이 4/6 시나리오에서 느렸다** (총 +29%). 시나리오별: S01 +106s,
S06 +134s, S10 +151s 느려지고 S05 −65s, S09 −40s 빨라졌다.

⇒ **우회책은 핸디캡이 아니라 지름길이었다.** "파일을 통째로 재작성하라" 는 부분 편집 시행착오를
없애고, "`bash cat <파일들>` 로 읽어라" 는 탐색 단계를 건너뛰게 한다. 약한 모델의 결함을 막으려
만든 처방이 강한 모델의 **탐색 비용도** 줄이고 있었다. 표본이 시나리오당 2회라 +29% 를 단정할 수는
없지만, "우회책이 Claude 를 붙잡고 있다" 는 가설은 **지지되지 않는다**.

## 결과 3 — 측정 도구가 약한 호스트의 문체에 적합돼 있었다

이번 측정의 가장 큰 소득이다. 호스트를 바꾸자 **oracle 오탐 3종 7건 + 분류기 결함 1건**이 터졌고
전부 산출물을 직접 열어 반증했다. 네 건 모두 **내 것**이다.

| # | 결함 | 원인 | 로컬 159회에서 안 드러난 이유 |
|---|---|---|---|
| 1 | O7 반박문 오탐 | "criterion flagged as missing **is actually satisfied**" 의 `missing` 만 보고 결함 서술로 판정 | 32B 는 노트가 짧고 단정적 — 반박문을 쓰지 않는다 |
| 2 | O7 메타·기대동작 오탐 | "my earlier verdict was **wrong**"(자기 정정), "dividing by zero **fails** with ValueError"(정상 동작) | 동일 |
| 3 | O6 docstring 오탐 | 정규식이 `def f(x: float) -> float:` 의 **반환 어노테이션**을 못 넘음 | 32B 는 타입 힌트를 쓰지 않는다 |
| 4 | 분류기 INFO fallthrough | O7 을 INFO 로 강등하니 INFO 만 있는 기록이 "findings 없음" 분기를 못 타고 맨 아래 `else: BUG` 로 떨어짐 | 강등 자체가 이번에 한 수정이라 신규 |

**이대로 비교했다면 "Claude 가 거짓 결과를 8% 낸다" 는 정반대 결론**을 냈을 것이다. 말을 조리 있게
하는 호스트가 체계적으로 불리해지는 편향이었다.

### 수정
- **O6**: 정규식 → `ast` 파서. 어노테이션·데코레이터·다중행 시그니처에 무관. 4조합 검증 통과
- **O7**: 키워드로는 정밀도 회복 불가(관측 4/4 오탐 = 정밀도 0) → `ACCURACY` → **`INFO`(수동확인)** 강등.
  거짓 결과 탐지는 결정론 oracle(O2 ground truth / O3 최종판정 대조 / O4 환각파일 / O8 공허테스트)이 담당
- **분류기**: `INFO` 는 판정 비관여 (`findings_v` 로 분리)

O7 강등·O6 수정은 **오탐만 줄이므로** 기존 로컬 기준선(측정 08: ACCURACY 0/159)은 유효하다.

> **교훈**: oracle 은 검증 대상의 출력 분포에 조용히 적합된다. 159회를 통과한 측정기가 호스트를
> 바꾸는 것만으로 4건의 숨은 가정을 드러냈다. **측정기를 다른 대상에 한 번 대보는 것**이
> 표본을 늘리는 것보다 강한 검증이다.

## 결과 4 — Nemotron 3 Nano 30B 타진 (1~2단계)

`nemotron-3-nano:30b` (31.6B MoE, 활성 3.5B, Q4_K_M 24.3GB) 를 받아 재보았다. GPU 는 24GB.

| 항목 | nemotron `think=false` | nemotron `think=true` | qwen2.5:32b |
|---|:-:|:-:|:-:|
| 생성 속도 | **21.7 tok/s** | 23.6 tok/s | 16.7 tok/s |
| VRAM / CPU 오프로딩 | 19.7GB / **6.86GB (25%)** | — | 19.7GB / 1.5GB (7%) |
| 산출물 (동일 codegen 프롬프트) | 코드블록 3개, PASS·docstring ✅ | **코드블록 0개, PASS 누락** | 코드블록 2개, ✅ |
| thinking 소비 | 0자 | **1557자** (400토큰 예산을 추론에 소진) | — |

**속도는 qwen 보다 30% 빠르다** — 25% 오프로딩에도 MoE 활성 3.5B 이점이 살아 있다.

**단 `think=false` 가 필수 조건이다.** 첫 워밍업(16토큰)에서는 `response` 가 **빈 문자열**이고 내용
전부가 `thinking` 필드로 갔다(`done_reason: length`). 우리 드라이버는 `verify_loop record` 실행,
`VERDICT:` 한 줄, 항목형 `M1: met | 증거` 같은 **엄격한 형식**을 응답에서 파싱하므로, 추론이 예산을
먹으면 형식이 아예 나오지 않는다.

남은 관문은 **OpenCode 가 `think=false` 를 전달할 수 있는지**다. 우리는 Ollama 를 직접 호출하지 않고
OpenAI 호환 엔드포인트를 경유하므로 Ollama 고유 파라미터가 전달되지 않을 수 있다. 전달 불가면
Modelfile 로 추론이 꺼진 파생 태그(`PARAMETER think false`)를 만드는 우회책이 있다.

## 부수 성과 — 완주 실패 원인 3분류

로컬 실패를 driver_tail 로 분류하니 원인이 서로 달랐다. **한 개선이 셋을 다 고치지 못한다.**

| 실패 | 원인 | 성격 |
|---|---|---|
| S09 | `'_total' 없음 / '_s(' 남아있음` **동일 진단 3회** 반복, 매번 전체 재작성만 함 | 하네스가 고칠 수 있음 (피드백 형태) |
| S05 | `divider.py` 를 2회 시도 끝에 **생성하지 못함** | 부분적으로 고칠 수 있음 |
| S01·S06 | unittest 가 `OK` 만 출력해 기대 토큰 `PASS` 미충족 | **모델 한계** — 기존 처방(unittest 금지 + 코드 템플릿)이 이미 발동한 뒤에도 3회 실패 |

S01·S06 은 처방이 **없어서** 실패한 게 아니라 처방을 **따르지 못해서** 실패했다. 하네스는 정확히
검출하고 정직하게 에스컬레이션했다 — 모든 실패를 하네스가 고쳐야 하는 것은 아니다.

## 비용

Claude 구간은 실측 과금 대상이다. 사이클당 claude 호출은 driver_tail 관측 기준 최소 5회이고
(테일 1200자만 보관하므로 하한값), 24 사이클(원본 12 + lean 12)을 돌렸다. 정확한 지출은 사용량
화면에서 확인해야 한다 — `--output-format json` 으로 토큰을 뽑으면 드라이버의 출력 파싱이 깨지므로
호출 횟수·벽시계만 계측했다.
