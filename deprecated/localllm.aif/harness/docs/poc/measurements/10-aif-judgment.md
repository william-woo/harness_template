# 측정 10 — AIF 항목형 판정 (F028 / ADR-020)

> 대상: `localllm.aif` (부모 `localllm` 과 A/B) · OpenCode 1.16.2 + Ollama 원격
> · 판정 모델 `qwen2.5:32b-instruct-q4_K_M`
> 적합도 함수: 무인 스위트 S06(다중 파일 import 체인) · S09(행위 보존 리팩토링)

## 무엇을 측정했나

RLAIF/CAI 문헌의 판정 설계 규율(항목형 채점표 + 증거 강제 + 앙상블 + UNCERTAIN)을 이식했을 때
① 로컬 32B 가 엄격 형식을 따를 수 있는지 ② 실제 사이클에서 지적이 주입되는지 ③ 부모 대비
스위트 통과율이 달라지는지.

**전체 적용이 아니라 전용 변형**(`claude.aif` / `localllm.aif`)에 격리한 이유는 부모를 남겨두지
않으면 차이를 구별할 수 없기 때문이다 (ADR-020 결정 1).

## 1차 실행(v1) — 판정 100% 무효, AIF 무동작

첫 A/B 의 aif 구간에서 항목형 판정이 **전부 무효**로 처리돼 주입이 0건이었다. 사이클은 정상
완주했지만 AIF 는 지연만 늘렸다 (S06: aif 257초 vs base 173초).

```
[aif] S06 PASS exit0 257s
   → AIF 항목 판정(reviewer) 전부 무효 — 주입 없음
   → AIF 항목 판정(qa) 전부 무효 — 주입 없음
```

### 결함 1 — 판정 대상 내용을 프롬프트에 주지 않았다 (설계 결함)

원인을 추정하지 않고 실제 응답을 확인했다:

```
It appears there was an attempt to use a tool that requires a URL starting with `http://` …
✗ WebFetch file://localhost/path/to/repo/word_count.py failed
  Error: URL must start with http:// or https://
→ validate: 누락 ['M1','M2','M3','M4','M5','M6','S1','S2','S3','S4']
```

파일**명**만 주고 내용도, 읽는 방법도 주지 않았다. 모델은 `WebFetch file://…` 로 파일을 읽으려
시도하다 실패하고 산문을 반환했고, 10개 항목이 전부 누락돼 판정 전체가 무효가 됐다.

드라이버의 기존 judge 프롬프트는 "bash `cat` 으로 읽어라"를 명시하는데, 내 항목형 프롬프트는
그 경로도 파일 내용도 제공하지 않았다.

**수정**: `build_prompt(context=...)` 로 대상 내용을 프롬프트에 담고 **"도구를 쓰지 말고 주어진
내용만으로 판정하라"**를 명시. `cycle_driver` 는 기존 `_files_context()` 를 그대로 전달한다.
판정 입력을 결정론적으로 고정하는 효과도 있다.

### 결함 2 — 부재 주장에 위치 증거를 강요했다 (설계 결함)

결함 1 을 고친 뒤 재진단에서 드러났다. 판정은 유효해졌지만 증거 검증이 이렇게 걸렸다:

| 항목 | 판정 | 증거 검증 |
|---|---|---|
| M1 docstring | unmet | — (정확: 대상 함수에 docstring 없음) |
| M2 단위 테스트 | met | ✅ `test_word_count.py:3` |
| M4 보안 | met | ❌ "파일:행 또는 인용 증거 없음" |
| M5 Surgical Changes | met | ❌ "파일:행 또는 인용 증거 없음" |

M4("자격증명 하드코딩 없음")·M5("무관한 변경 없음")는 **없음을 주장하는 항목**이라 원리상
`파일:행` 증거가 존재할 수 없다. 위치 증거를 강요하면 이 항목들이 항상 무효화되고, MUST 에
UNCERTAIN 이 하나라도 있으면 전체가 `uncertain` 이므로 **게이트가 상시 에스컬레이션**된다.

**수정**: rubric 항목에 `증거유형: 부재` 를 표시하고(M4/M5/M6/S3), 해당 항목은 **확인한 범위
서술**(20자 이상)로 검증한다. 위치형 항목의 엄격성은 그대로 유지한다.

> 측정 08 의 "거짓 부재" 결함과 대칭 관계다. 그때는 judge 의 부재 주장에 증거를 요구했고,
> 여기서는 부재 항목에 **다른 종류의 증거**를 허용해야 했다. 증거 강제는 항목의 논리적 성격에
> 맞춰 설계해야 한다.

### 수정 후 검증

같은 대상에 2회 판정:

```
판정 1: valid=True 증거결함={}
판정 2: valid=True 증거결함={}
앙상블 최종: revision
  M1 unmet   {'unmet': 2}     ← docstring 누락을 2/2 합의로 검출
  M2 met     {'met': 2}
  M3 na      {'na': 2}
  M4 met     {'met': 2}
  M5 met     {'met': 2}
  M6 met     {'met': 2}
```

S03(AC 준수 — docstring 누락 검출)이 시험하는 실패 유형을 항목형 판정이 **2/2 합의로** 잡았다.
무효 사유를 로그에 남기도록 보강해 다음 실패는 driver_tail 만으로 진단된다.

## 2차 실행(v2) — 부모 대비 A/B

설계: S06·S09 를 3라운드, 라운드마다 `localllm`(base) → `localllm.aif`(aif) 구간을 교대.
측정 09 에서 배치 간 분산이 크다는 것이 확인됐으므로 **같은 배치 내 교대**로 짰다.
두 변형의 `run_suite.py` 는 동일하고 차이는 `cycle_driver._aif_findings` 주입뿐이다.

비용: 항목형 판정은 역할당 2회 추가 호출이므로 aif 구간이 구조적으로 더 느리다 (예상된 차이).

### 결과 — 통과율 동률, 비용 2.4배

| 구간 | PASS | 라운드 순서 (r1→r3) | 완주 평균 | AIF 발화 |
|---|:-:|---|:-:|---|
| base (`localllm`) | **3/6 (50%)** | 🤖🤖 ✅✅ ✅🤖 | 142s | — |
| aif (`localllm.aif`) | **3/6 (50%)** | ✅✅ 🤖🤖 ✅🤖 | 334s | 6회 (revision 5 / pass 1), 지적 12건 |

**통과율 차이 0.** AIF 경로는 정상 발화했고(6회 중 5회 revision·1회 pass — 항목별로 갈린다)
지적 12건이 실제로 주입됐다. 즉 **경로는 살아 있는데 통과율은 움직이지 않았다.**

라운드별로 결과가 뭉쳐 있는 것이 눈에 띈다 — base 는 r1 전패·r2 전승, aif 는 r1 전승·r2 전패.
판정 품질이 아니라 **라운드 조건이 지배한다**는 신호이고 측정 09 의 재현이다.

세 해석이 가능하고 이 데이터로는 구분할 수 없다: ① 판정 개선이 통과율에 영향이 없다
② 영향은 있으나 n=6 에 묻혔다 ③ 지적이 늘어 revision 이 늘어난 만큼 재작업 기회도 늘어 상쇄됐다.

비용은 명확하다 — 완주 평균 334초 대 142초(**2.4배**). 역할당 판정 2회 추가에 재작업 라운드
증가가 겹친 결과로 보인다.

⇒ **스위트 통과율은 판정 품질 개선을 측정하는 도구가 아니다.** 사이클 전체의 분산이 판정 차이를
덮는다. 그래서 판정 자체를 재는 측정으로 넘어갔다.

## 3차 — 판정 분산 직접 측정 (24 판정 호출)

결함을 심은 고정 대상에 N=6 회씩 판정하고, **같은 내용 · 구조만 다르게** 두 구간을 비교한다
(둘 다 도구 미사용 — 공정성 조건). `tests/judge_variance.py`.

| 케이스 | ground truth | 산문형 정답률 | 항목형 정답률 | 항목형 M1 |
|---|---|:-:|:-:|:-:|
| `no_docstring` (미탐 시험) | revision | **6/6 (100%)** | **6/6 (100%)** | unmet 6/6 |
| `clean` (오탐 시험) | pass | **1/6 (16%)** | **4/6 (66%)** | met 6/6 |

`clean` 케이스 분포:
- 산문형: `pass` 1 · **`unparseable` 3** · `revision` 2
- 항목형: `pass` 4 · `revision` 1 · `uncertain` 1 · **무효 0**

### 관찰 1 — 명백한 결함에는 개선 여지가 없다 (천장 효과)
docstring 누락은 산문형으로도 6/6 으로 잡힌다. 이런 케이스로는 두 구간을 구별할 수 없다.
**판정 개선을 재려면 오탐 케이스가 필요하다.**

### 관찰 2 — 차이는 오탐에서 나타났다 (16% → 66%)
정상 산출물에 산문형은 2회 `revision` 을 냈다. 산문형 MUST 에 "에러 처리 — 외부 I/O 경계에서
방어"가 있는데, 단순 문자열 분할 함수엔 그런 경계가 없다. judge 가 이를 "미해결"로 읽은 것이다.
항목형 M3 에는 `판정: 경계가 없는 순수 로직 변경이면 na` 라는 처리 규칙이 있어 이 오탐을 줄였다.

⇒ **구조화의 이득은 "결함 검출"이 아니라 "해당 없음을 해당 없음으로 판정하는 능력"에서 나왔다.**

### 관찰 3 — 형식 준수율이 갈렸다 (50% → 100%)
산문형은 6회 중 **3회가 형식 위반**으로 verdict 를 추출할 수 없었다. 반면 항목형은 12회 판정
전부 유효(무효 0)였다 — 10개 항목을 정해진 줄 형식으로 요구하는 **더 엄격한** 형식인데도 그렇다.

> 유보: 산문형의 `VERDICT:` 형식 요구는 내가 설계한 것이므로, 3회 위반에 내 프롬프트 설계 책임이
> 섞여 있다. 다만 항목형이 훨씬 엄격한 형식에서 100% 준수를 얻었다는 점은 **구조가 준수를
> 가능하게 한다**는 해석을 지지한다. 표본은 셀당 6회다.

### 관찰 4 — `uncertain` 1건은 오류가 아니다
항목형 `clean` 에서 1회 `uncertain` 이 나왔다. 증거 결함으로 항목이 무효화돼 정직하게
에스컬레이션한 것이다 — 설계된 동작이지만 `pass` 도 아니므로 **비용으로 계산해야 한다**.

## 교훈

1. **판정자에게 판정 대상을 주지 않으면 판정이 아니라 환각이 나온다.** 도구 접근을 전제하지 말고
   필요한 내용을 프롬프트에 넣거나, 읽는 방법을 명시해야 한다.
2. **증거 강제는 항목의 논리적 성격에 맞춰야 한다.** 부재 주장에 위치 증거를 요구하면 게이트가
   상시 UNCERTAIN 으로 무력화된다 — 엄격함이 곧 유효함은 아니다.
3. **무동작은 실패보다 발견하기 어렵다.** 사이클은 완주했고 exit code 도 정상이라 결과만 보면
   문제가 안 보였다. 주입 건수를 로그에 남긴 것이 유일한 단서였다 — 새 게이트를 추가할 때는
   **그 게이트가 실제로 발화했는지 세는 로그**를 함께 넣어야 한다.
4. **개선을 측정할 도구를 잘못 고르면 개선이 없다고 결론 내리게 된다.** 스위트 통과율은 사이클
   분산이 커서 판정 품질 차이를 볼 수 없었다(3/6 대 3/6). 같은 변경을 판정 분산으로 재자
   16% → 66% 라는 큰 차이가 드러났다. **측정 대상과 개선 대상이 일치해야 한다.**
5. **천장 효과를 피하려면 오탐 케이스를 넣어야 한다.** 명백한 결함만 시험하면 두 구간이 모두
   만점이라 판별력이 0 이다. 정상 산출물을 정상으로 판정하는지가 실제 판별점이었다.
6. 이 두 결함은 F026 의 패턴을 반복한다 — 결함 38건 중 17건이 내 것이었다. 새 측정 도구를
   붙일 때 가장 먼저 의심할 대상은 **측정 도구 자신**이다.
