# ADR-022: 모델의 선의에 기대지 않는 하네스 — 스키마 파생 도구 지시

> Feature: F031 — nemotron 기반 하네스 템플릿 (localllm.nem 재구성)
> 상태: `Accepted` (설계 — 구현·실측 진행 중)
> 관련: ADR-021(모델 축 분기), ADR-009(OpenCode 어댑터), ADR-018(결정론 supervisor),
> 측정 11 결과 13(지시문 결함 실측), F031 제품 brief

## 맥락

측정 11 결과 13 이 드러낸 사실 하나가 이 ADR 전체의 출발점이다.

하네스는 파일 생성을 이렇게 지시하고 있었다:

```
Call the edit tool with filePath exactly "foo.py" ... and the complete file content.
```

그런데 OpenCode 스키마는 이렇다:

| 도구 | required |
|---|---|
| `edit` | `filePath`, `oldString`, `newString` |
| `write` | `filePath`, `content` |

`edit` 에는 `content` 가 **없다**. 이 지시는 **만족 불가능**했다. 그럼에도 스위트가 통과해온
이유는 하나다 — **qwen 이 지시를 무시하고 `write` 를 불렀기 때문이다.** 지시를 문자 그대로
따르는 nemotron 은 실패했다. 수정 후 nemotron 은 **5/5** 로 성공했다.

교훈은 nemotron 에 관한 것이 아니다:

> 우리 하네스는 **모델이 우리 실수를 교정해 준다는 전제** 위에 서 있었고,
> 그 전제는 문서 어디에도 적혀 있지 않았다.

## 결정

### 결정 1 — 도구 지시를 손으로 쓰지 않고 스키마에서 파생한다

도구 이름과 인자를 프롬프트에 **직접 타이핑하지 않는다.** 스키마 스냅샷을 두고 지시문을
거기서 생성한다.

```
.claude/schema/opencode-tools.json     # 도구 스키마 스냅샷 (이름 · required · properties)
```

`cycle_driver` 는 "파일을 만들라"는 의도를 주고, 문구는 스냅샷의 `write` 정의에서 만든다.
스키마가 바뀌면 지시문이 함께 바뀐다.

**왜 스냅샷인가**: 런타임에 전체 스키마를 얻는 경로가 없다 (실측).

| 얻고 싶은 것 | 런타임 경로 | 결과 |
|---|---|---|
| 도구 **이름·활성 여부** | `opencode debug agent <role>` | ✅ 가능 (`tools: {write: true, ...}`) |
| 도구 **파라미터 스키마** | 없음 | ❌ 프록시 캡처로만 |

따라서 스냅샷은 **프록시 1회 캡처로 생성**하고 템플릿에 넣어 배포한다. 갱신은 명시적 작업이다.

### 결정 2 — 스키마 정합성을 자동 검사로 강제한다

스냅샷이 있어도 사람이 프롬프트에 도구 이름을 손으로 쓰면 같은 결함이 재발한다.
**검사기**를 둔다 (F031 성공지표 S3):

- 프롬프트 문자열에 등장하는 도구 이름을 수집한다
- 그 도구에 대해 요구하는 인자가 스냅샷의 `required`/`properties` 와 어긋나면 **BLOCK**
- "edit 에 content 를 넘겨라" 같은 지시는 이 검사에서 걸린다

검사는 모델 호출 없이 **정적**으로 돈다 — 결정론 grader 우선 원칙(ADR-014)과 같은 계열이다.

### 결정 3 — 문자 그대로 따라도 성립하는 지시만 쓴다

프롬프트 규율에 항목을 추가한다:

> 지시는 **문자 그대로 이행 가능해야** 한다. 모델이 의도를 추측해 교정해 주는 것에
> 기대지 않는다. 지시가 도구·인자·경로를 지목하면, 그 지목이 실제 스키마와 일치해야 한다.

이는 기존 "강지시어 절제 / 검증 지시 중복 금지"와 층위가 다르다. 그 둘은 **과잉**을 막고,
이 항목은 **불이행 가능한 지시**를 막는다.

### 결정 4 — 예산은 실측된 필요량 위에서 정한다 (도그마 없이)

`limit.output` 을 정하는 규칙:

| 근거 | 값 |
|---|---|
| nemotron 관측 추론 지출 | 2043~3099자 (≈ 500~800 토큰) |
| 도구 인자(파일 본문) | 과제 의존 |
| 현재 채택값 | **4096** — 이 값에서 5/5 성공 (실측) |

- **낮추기 금지**: 근거 없이 기본값 아래로 내리지 않는다. 실제로 내 초기 설정이 기본 32000 을
  4096 으로 낮췄고, 그것이 옳았는지는 실측으로만 확인됐다.
- **올릴 신호**: 응답에 `finish_reason == "length"` 가 관측되면 올린다. 결과 12 는 이 신호
  **없이** 16384 로 올려 봤고 산출물은 동일했으며 시간만 67% 늘었다 — 신호 없는 상향은 순손실이다.
- `limit` 은 `context` 와 `output` 을 **둘 다** 요구한다. 하나만 넣으면 OpenCode 가
  `Configuration is invalid` 로 전 실행을 거부한다 (실측 — 배치 2개를 날렸다).

### 결정 5 — 재시도 횟수를 측정된 성공률에서 정한다

`_ensure_files` 의 파일당 2회 시도는 qwen 관측에서 나온 값이다. 근거를 실측으로 교체한다.

| 모델 | 1회 성공률 (실측) | 2회 누적 |
|---|---|---|
| nemotron (수정 후) | 5/5 ~ 6/7 ≈ 86~100% | ≥ 98% |

현재 값 **2회를 유지**한다 — 다만 이제 근거가 있다. 성공률이 이 아래로 떨어지면 올린다.

### 결정 6 — 검증에 대조군을 둘 층위로 요구한다

이번 조사에서 **계측 도구가 만든 착시가 5건**이었고, 그중 하나는 "모델이 도구를 안 불렀다"는
오판을 만들었다. 따라서 대조군은 모델에만 두지 않는다.

| 층위 | 대조군 | 규칙 |
|---|---|---|
| 모델 | qwen2.5:32b 동일 배치 | 대조군 실패 시 그 배치 판정 폐기 |
| **계측 도구** | 알려진 정상 모델을 **먼저** 통과시킨다 | 프록시·샌드박스를 고친 뒤 대조군으로 도구 건강을 증명하고 나서 판정 |

### 결정 7 — 부모 `localllm` 은 이 설계의 수혜자이되 기준은 유지한다

결정 1~3 은 모델 무관 개선이므로 부모에도 적용한다 (edit→write 수정은 이미 적용).
다만 부모의 **모델 배정은 qwen 기준으로 불변** — 대조군을 보존한다 (ADR-021 결정 1).

## 대안 검토

| 대안 | 기각 이유 |
|---|---|
| 지시문을 손으로 고치고 끝 | 이번 1건은 고쳐지지만 재발을 막지 못한다. 실제로 이 결함은 오래 숨어 있었다 |
| 런타임에 매번 스키마 조회 | 전체 스키마를 주는 런타임 경로가 없다 (실측). 프록시를 상시 끼우는 것은 과하다 |
| 도구 지시를 아예 빼고 모델에 맡김 | 측정 08 이 기록한 실패(절대경로 날조·상대명 훼손)가 돌아온다. 지시는 필요하다 — **정확해야** 할 뿐이다 |
| nemotron 을 포기하고 qwen 유지 | 문제를 드러낸 장치를 없애는 선택. 결함은 남고 발견 수단만 사라진다 |
| 예산을 넉넉히 올려 두기 | 결과 12 실측 — 이득 0, 시간 67% 증가 |

## 비용

- 스냅샷 갱신은 **수동 작업**이다 (프록시 1회). OpenCode 업스트림이 도구 스키마를 바꾸면
  갱신 전까지 검사기가 낡은 기준으로 검사한다 — 검사기가 "스냅샷 나이"를 함께 보고한다.
- 검사기 1종 추가 → lint 실행 시간 소폭 증가 (정적 검사라 무시할 수준).
- nemotron 은 같은 과제에 qwen 의 3~5배 시간이 든다 (104~158초 대 28~30초). 로컬 추론이라
  과금은 0 이고, F031 은 속도를 비목표로 명시했다.
