# ADR-021: 모델 전용 변형 분기 — localllm.nem (nemotron 기반 하네스)

> Feature: F030 — localllm.nem 변형 신설 (후속 F031 = localllm.gem)
> 상태: `Accepted` (구현 — 변형 신설 + 추론 예산 등재 자동화. 스위트 A/B 는 진행 중)
> 관련: ADR-009(OpenCode 호스트 어댑터), ADR-017(localllm loope 계보), ADR-019(autoresearch),
> 측정 11 결과 8·10(모델 판정 무효화 → 추론 예산이 진짜 원인)

## 맥락

`localllm` 변형은 qwen2.5 2 티어(14B 생성형 / 32B 판정)로 고정돼 있었다. 다른 로컬 모델을
평가하려던 시도(측정 11 결과 6·7)는 gemma4·nemotron 을 **"도구 호출 관문 탈락"** 으로 판정했고,
그 판정은 결과 8 에서 방법론 결함으로 전수 무효화됐다.

결과 10 이 진짜 원인을 찾았다 — **추론 예산 잠식**이다:

| 모델 | Ollama 능력 선언 | 도구 호출 전 지출 | `max_tokens=400` 결과 |
|---|---|---|---|
| `qwen2.5:32b` | `completion, tools` | 없음 (즉시 호출) | 정상 |
| `gemma4:26b` | `completion, vision, tools, **thinking**` | ≈500 토큰 | `tool_calls=0`, `finish=length` |
| `nemotron-3-nano:30b` | `completion, tools, **thinking**` | 동종 | 절단 관측 |

추론 모델은 도구를 호출하기 **전에** 추론 토큰을 쓴다. 예산이 부족하면 추론 중간에서 잘려
도구 호출 델타가 아예 생성되지 않는다. 모델은 무엇을 해야 하는지 알고 있었다 — 프로브가 잡은
추론 원문이 *"I should use the `edit` tool for this"* 였다. **말할 지면이 없었을 뿐이다.**

즉 우리 하네스가 "qwen 에서만 동작"한 것은 모델 편애가 아니라 **추론 예산을 고려하지 않은
파이프라인**에 추론 모델을 넣었기 때문이다. 이 사실을 안 이상, 모델 축의 평가는 다시 열린다.

## 결정

### 결정 1 — 부모를 고치지 않고 모델별 변형으로 분기한다

`localllm` → **`localllm.nem`**(nemotron) / **`localllm.gem`**(gemma) 으로 복사해 각자
모델 축만 다르게 둔다. 부모 `localllm` 은 qwen2.5 기준으로 **그대로 유지**한다.

이유는 ADR-020 결정 1 과 같다 — **부모를 바꾸면 차이를 측정할 대조군이 사라진다.** 부모의
측정 01~09 는 qwen 조건에서 얻은 것이고, 그 위에 모델을 갈아끼우면 기존 실측이 전부 해석
불가가 된다. 세 변형이 공존해야 "모델을 바꾸면 무엇이 달라지는가"에 답할 수 있다.

### 결정 2 — 티어를 두지 않고 단일 모델을 전 9 역할에 쓴다

부모는 32B 기본 + gatekeeper 14B 구성이다 (ADR-017 개정 4-bis). 이 변형은 `nemotron-3-nano:30b` 하나를 전 역할에 쓴다.
`nemotron-mini`(4.2B) 는 provider 에 **등재만 하고 역할 배정은 하지 않는다**.

목적이 "nemotron 계열의 성능 측정"이기 때문이다. 경량 티어를 섞으면 미검증 4.2B 가 판정에
변수로 들어가고, 결과가 나빠졌을 때 원인이 nemotron 인지 티어 배분인지 구별할 수 없다.

### 결정 3 — 추론 예산을 설치 스크립트가 등재·보정한다

`opencode-setup.sh` 가 전역 설정에 모델을 등재할 때 `limit: {context, output}` 을 함께 넣고,
**이미 `limit` 없이 등재된 항목도 보정**한다.

프로젝트 `opencode.json` 에만 넣는 것으로는 부족하다 — 측정 08 발견 2 가 확인했듯 OpenCode
1.16.2 는 프로젝트 설정의 `provider.*.models` 를 **모델 해석에 반영하지 않는다**. 템플릿은
값을 문서로 지니되, 실제 적용은 설치 스크립트가 전역에 심어야 한다.

`limit` 은 `context` 와 `output` 을 **둘 다** 요구한다. 하나만 넣으면 OpenCode 가
`Configuration is invalid` 로 **모든 실행을 즉시 거부**한다 (이 함정을 개발 중 실제로 밟았고,
그 결과 3 구간 배치 2 개가 "환경 정지"로 오진됐다 — 대조군이 함께 실패해 폐기됐기에 잘못된
결론이 기록되지는 않았다).

### 결정 4 — 관측된 약점에만 정책을 둔다

`.claude/policy/{reviewer,qa}.md` 만 추가한다. 부모에서 nemotron 이 보인 실패는 판정 단계에서
**기록 도구를 호출하지 않고 산문으로 답하는 것**이었다. 정책은 그 하나를 겨눈다 — 추론을
끝냈으면 `verify_loop.py record` 를 bash 로 실행하고 답을 마쳐라.

developer 등 다른 역할에는 정책을 두지 않는다. 관측되지 않은 약점에 대한 처방은 추측이고,
`.claude/policy/README.md` 의 작성 규칙(작업 방식만, 5줄 이내)에도 어긋난다.

## 원본(부모 변형)과의 차이

| 항목 | `localllm` (부모) | `localllm.nem` |
|---|---|---|
| 모델 | qwen2.5 14B/32B 2 티어 | `nemotron-3-nano:30b` 단일 |
| 추론 모델 | ❌ | ✅ — 예산 관문이 추가됨 |
| 전역 등재 | `{"name": ...}` | `{"name": ..., "limit": {...}}` + 누락 보정 |
| 정책 오버레이 | 없음 (README 만) | `reviewer.md` · `qa.md` |
| 측정 기록 | 측정 01~11 (qwen 조건) | 부모 기록을 **그대로 보존** — 위조하지 않는다 |

`docs/poc/measurements/*` 는 부모 조건의 실측이므로 nemotron 으로 고쳐 쓰지 않는다. 기록을
모델명만 바꿔 재사용하는 것은 증거 위조다. nemotron 등급은 `MODEL-GRADES.md` 에 **별도 절**로
덧붙이고, 확인된 것과 미검증을 표로 구분해 적는다.

## 대안 검토

| 대안 | 기각 이유 |
|---|---|
| 부모 `localllm` 의 모델만 교체 | 대조군 소멸 — 측정 01~09 가 해석 불가가 된다 |
| 모델을 환경변수로만 전환 (변형 무분기) | 모델별로 달라지는 것이 모델명뿐이 아니다 — 예산·정책·문서가 함께 간다 |
| gemma 를 먼저 착수 | 스모크에서 nemotron 은 기대 출력을 냈고 gemma 는 출력이 비었다. 확실한 쪽부터 |
| `nemotron-mini` 를 gatekeeper 에 배정 | 미검증 4.2B 가 결과 해석에 변수를 더한다 (결정 2) |

## 비용

- 변형 하나당 210 파일 · 2.7MB. 부모 변경 시 미러 대상이 2 개 늘어난다 (LINT-MR-9~13 이 강제).
- 추론 예산은 **도구 호출마다 추론 토큰**을 붙인다. 로컬 추론이라 과금은 0 이지만 벽시계는 늘어난다.
  `VERDICT: pass` 13 자를 얻으려 추론 수백 토큰을 쓰는 비효율이 판정 단계에 구조적으로 남는다.
- 완주율 이득이 이 지연을 상쇄하는지는 **스위트 A/B 로 판정한다** — 그 전까지 이 변형의
  성능 우위는 주장하지 않는다.

## 결과

- `localllm.nem` 신설 (210 파일), LINT-MR 6 개 목록에 등재 — **113 PASS / 0 BLOCK**.
- 스모크: `nemotron-3-nano:30b` rc=0 / 46s / 기대 출력 일치. **qwen 대조군 동시 통과**로 유효.
- 미검증: 도구 호출 성립 · 사이클 완주율 · 판정 품질 — 스위트 A/B 대기.
