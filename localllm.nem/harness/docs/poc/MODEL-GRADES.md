# d-2 로컬 LLM 모델 등급 — 작업별 적합 모델 (F015 실측 기반)

> OpenCode + Ollama 환경에서 하네스 역할별로 어느 크기의 로컬 모델이 필요한가.
> **추측이 아니라 PoC 5회 실측**(docs/poc/measurements/) 기반. 측정 환경:
> OpenCode 1.16.2 + Ollama (172.16.10.217, RTX 4500 24GB).

## 핵심 결론 (한 줄)

**현실적 SDLC 부하에서는 생성도 32B 가 필요하다 (측정 08 개정).** 판정·loope 도구 조작은 32B,
멀티스텝 값 전달(G4)은 32B 에서도 실패해 파일 핸드오프·결정론 도구로 우회한다.
14B 는 단일 파일·단순 과제(측정 02·04)엔 충분하지만, **다중 파일 + AC 준수 + 테스트 동반**
과제에서는 기계적 산출물 결함(리터럴 개행 / 이스케이프 유출 / 탭 혼용 / "" 인용부호)과
지시 불이행(docstring 추가·요구 출력)을 반복해 3라운드 연속 수렴 실패했다. 같은 하네스·같은
시나리오에서 32B 는 judge 지적을 받아 스스로 고쳐 **완주(exit 0)** 했다.

d-2 에서 "로컬 LLM 으로 하네스가 되는가?"의 답은 **모델 크기에 좌우되는 작업 등급**에 달려 있다.

## 신뢰성 경고 — 산출물은 반드시 파일시스템·테스트로 검증한다 (측정 08)

"쓰기 성공 보고 후 파일 없음" 을 여러 차례 관측했으나, **주 원인은 호스트가 상대경로를 `PWD`
환경변수 기준으로 해석하는 것**이었다 (드라이버가 `subprocess(cwd=)` 만 지정해 파일이 상위
디렉토리에 생성됨 — 전수 검색으로 확인, `cycle_driver` 가 `PWD` 를 명시하도록 수정). 모델·호스트는
정직하게 보고하고 있었다. **정정 기록**: 초기에 이를 환각으로 판정했던 것은 오진이었다.

실제로 관측된 모델 측 결함은 다음이다:
- **경로 날조**: 에이전트 미지정 모드에서 "write 도구는 절대경로가 필요하다" 고 오판해
  `/current_directory/...`, `/path/to/...` 를 생성 → 권한 거부 (모델 출력으로 직접 확인)
- **리터럴 개행**: 파일 내용에 실제 줄바꿈 대신 두 글자 `\n` 을 기록 → 파일 전체가 한 줄
  주석이 되어 테스트가 조용히 exit 0 (기대출력 검사가 차단 — `_artifact_problems` 로 진단)
- **요구 출력 무시**: AC 가 `print('PASS')` 를 명시해도 관용적 `unittest` 로 바꿔 "OK" 만 출력

⇒ 결론은 동일하다: **에이전트의 산출 보고를 신뢰하지 말고** 드라이버·grader 가 파일 존재·형식·
테스트 출력으로 검증해야 한다 (`_ensure_files`, `_artifact_problems`, `--expect`).

## 최난이도 등급 — 다중 파일 + import 체인 (측정 08: 7라운드 전패 → R19 첫 통과)

`greet.py` + `names.py` + `test_greet.py` (import 체인 + 상수 + 기본값 + AC 준수) 과제는
**7라운드 모두 실패**했다. 매 라운드 실패 양상이 달랐다:

| 라운드 | 실패 양상 |
|---|---|
| 11~13 | 이스케이프 유출 → 문법 오류 (리터럴 `\n`, `\"`) |
| 14 | 거짓 revision (judge 가 실재하는 DEFAULT_NAME 을 없다고 주장) |
| 15 | 닫히지 않은 문자열 리터럴 |
| 16 | 'lacks' 표현 거짓 주장 → 반박 미발동 |
| 17 | **모듈 미생성 + 테스트에 함수 직접 정의** (AC 회피) |
| 18 | 수렴 실패 (MODEL) |

| 19 | ✅ **첫 통과 (exit 0 완주)** — greet.py 가 names 를 import 하고 docstring·테스트 모두 충족 |

⇒ **정정 (중요)**: 라운드 18 시점엔 이를 "32B 의 상한" 이라고 단정했으나, 라운드 19 에서
통과해 **반증됐다**. 상한이 아니라 **하네스 피드백 품질에 크게 의존하는 최난이도 등급**이다.
통과를 가능하게 한 누적 개선: 거짓 부재 반박 확장(기계점검을 증거원으로) / unittest 리터럴
금지 + 테스트 템플릿 / grader 실패 맥락 전달 / grader·judge 재시도 예산 분리.

⇒ **권고**: 이 등급은 재현율이 낮으므로(1/8) 중요 작업에서는 상위 호스트 검토를 병행하고,
다운스트림은 과제를 단일 파일 단위로 분해하는 편이 안정적이다. 단, 하네스는 8라운드 모두
실패를 정확히 검출하고 정직하게 에스컬레이션했다 (**거짓 통과 0**).

> **메타 교훈**: 무인 스위트는 모델·하네스의 결함뿐 아니라 **개발자의 성급한 일반화**도
> 반증한다. "7라운드 전패 = 상한" 은 표본이 개선 이전 구간에 몰려 있었기 때문이었다.
## 14B 의 기계적 산출물 결함 카탈로그 (측정 08)

로컬 14B 가 도구 인자 직렬화에서 반복하는 결함들. 각 변형을 **결정론 정규화**(compile 검증 후
채택)로 흡수했고, `--no-autofix` 로 끌 수 있다 (순수 측정용):

| 결함 | 증상 | 하네스 대응 |
|---|---|---|
| 리터럴 개행 | 파일 전체가 한 줄, 두 글자 백슬래시-n 다수 → 조용한 exit 0 | 진단 + unescape 정규화 |
| 이스케이프 유출 | 백슬래시-따옴표가 파일 내용으로 → 문법 오류 | 진단 + unescape 정규화 |
| 탭/스페이스 혼용 | TabError | 선행 탭 → 스페이스 4칸 |
| docstring 인용부호 | "" 로 열고 닫음 → 문법 오류 | """ 복구 |
| 경로 날조 | `/current_directory/`, `/path/to/` → 권한 거부 | `--agent` 모드 + 파일 존재 검증 |
| 지시 불이행 | docstring 미추가, 요구 출력(PASS) 무시, unittest 로 대체 | 기계 점검 사전제시 + 코드 템플릿 + `--expect` |
| 테스트 치팅 | 수정 금지 테스트 재작성, assert 없는 공허 테스트 | 파일 보호(복원+fail) + 공허 통과 차단 |

## 하네스 역할 → 최소 모델 등급

우리 7 에이전트를 작업 등급으로 분류하면:

**중요 (측정 04 데모 후속, 2026-06-10)**: "단일 역할"도 **생성형 vs 검증형**으로 갈린다.
- **생성형 (1홉)**: 프롬프트 → 코드/문서 산출. 14B OK.
- **검증형 (다홉)**: read → 실행 → 출력 해석 → 추론 → 판정. **본질적으로 멀티스텝**이라 G4 한계에 근접.
  reviewer 데모 4회 중 깔끔한 판정 0회 (증거 수집은 1회 성공, 나머지는 절대경로·권한·hang 으로 무산).

| 에이전트 | 작업 성격 | 14B 로 충분? | 비고 (측정 근거) |
|---|---|:-:|---|
| developer | **생성형** G1·G2 | ⚠️ **단순 과제만** | 측정 04 단일파일 PASS / **측정 08 다중파일·AC 과제에서 반복 실패** → 32B 권장. 결정론 게이트 + judge 피드백 루프 필수 |
| architect | **생성형** G1 | ✅ | ADR/설계 문서 생성 |
| designer | **생성형** G1 | ✅ | 토큰 추천 생성 |
| planner | **생성형** G1 | ⚠️ | 단순 분해 OK / 복잡 분해는 품질 편차 |
| reviewer | **검증형** G1+다홉 | ❌ | read·실행·추론·판정 = 멀티스텝. 데모 4회 판정 실패 → **32B+ 또는 사람/Claude Code** |
| qa | **검증형** G1+다홉 | ❌ | reviewer 와 동일 — 검증형은 14B 신뢰 어려움 |
| **orchestrate (커맨드)** | **G5** | ❌ | **32B+ 또는 흐름 단순화 필요** |

→ **생성형 단일역할(developer/architect/designer)은 14B 로 d-2 즉시 가능** (산출물은 "초안" — 검증 별도).
→ **검증형 단일역할(reviewer/qa)은 멀티스텝 성격이라 14B 불안정** — 32B+ 권장, 또는 검증을 사람/Claude Code 가 담당하는 **하이브리드**.
→ **orchestrate 같은 이종 핸드오프는 14B 한계** — 32B+ 또는 단일 스텝 분해.

## nemotron 등급 (localllm.nem 변형 — F030 / ADR-021)

> 위 등급표는 **부모 `localllm` 의 qwen2.5 실측 기록**이다 (F015·측정 02~09). 이 절은
> `localllm.nem` 변형이 쓰는 nemotron 계열을 별도로 기록한다. 두 계열은 **결정적으로 다른
> 성질**을 가지므로 등급을 그대로 옮길 수 없다.

### 계열 차이 — 추론 모델 여부

| 모델 | 크기 | Ollama 능력 선언 | 추론 모델 |
|---|---|---|:-:|
| `qwen2.5:32b-instruct-q4_K_M` | 19.9GB | `completion, tools` | ❌ |
| `qwen2.5:14b-instruct-q8_0` | 15.7GB | `completion, tools` | ❌ |
| `nemotron-3-nano:30b` | 24.3GB | `completion, tools, **thinking**` | ✅ |
| `nemotron-mini:latest` | 2.7GB (4.2B) | `completion, tools` | ❌ |

### 등급 이전이 불가능한 이유

qwen 등급표는 "몇 B 면 이 과제를 하는가"를 축으로 삼는다. nemotron 에는 그 축 **앞에** 다른
관문이 하나 더 있다 — **출력 예산**. 추론 모델은 도구를 호출하기 전에 추론 토큰을 먼저 쓰고,
예산이 부족하면 파라미터 수와 무관하게 도구 호출이 **0건**이 된다 (측정 11 결과 10).

즉 nemotron 의 실패는 두 종류로 갈린다:

| 실패 | 관측 신호 | 원인 | 대응 |
|---|---|---|---|
| 예산 부족 | `finish=length`, `tool_calls=0` | 설정 (하네스 책임) | `limit.output` 상향 |
| 능력 부족 | `finish=tool_calls` 인데 결과가 틀림 | 모델 (등급 문제) | 상위 모델 |

**첫 줄을 해결하기 전의 모든 능력 판정은 무효다.** 부모 변형에서 nemotron 을 "도구 호출 관문
탈락"으로 판정했던 측정 11 결과 6 이 그 오류였고, 결과 8·10 이 정정했다.

### 현재 확인된 것 / 확인되지 않은 것

| 항목 | 상태 | 근거 |
|---|---|---|
| `limit` 등재 후 정상 응답 | ✅ 확인 | 스모크 rc=0 / 46s / 기대 출력 일치. qwen 대조군 동시 통과 |
| 도구 호출 성립 | ⏳ 미검증 | 하네스 경로 스위트 필요 |
| 사이클 완주율 | ⏳ 미검증 | 부모 qwen 기준 4/6 과 비교 예정 |
| 판정(judge) 품질 | ⏳ 미검증 | 부모에서 관측된 약점은 **판정 기록 누락**(형식) — `.claude/policy` 로 대응 |
| `nemotron-mini` 경량 티어 | ⏳ 미검증 | provider 등재만, 역할 배정 없음 |

### 운영 가이드

```bash
# 전역 등재 (limit 포함 — 이 단계를 빠뜨리면 도구 호출이 무산된다)
bash .claude/bin/opencode-setup.sh

# 예산을 바꾸려면
OLLAMA_OUTPUT=8192 bash .claude/bin/opencode-setup.sh
```

> **예산의 비용**: 도구 호출마다 추론 토큰이 붙는다. `VERDICT: pass` 13자를 얻으려 추론
> 수백 토큰을 쓰는 비효율은 구조적으로 남는다 — 로컬 추론이라 과금은 0 이지만 **벽시계는
> 늘어난다**. 완주율 이득이 이 지연을 상쇄하는지는 스위트 비교로 판정한다.
