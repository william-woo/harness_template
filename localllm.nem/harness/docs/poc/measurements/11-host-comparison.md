# 측정 11 — 호스트 성능 비교와 측정 도구의 숨은 가정 (F029)

> 대상: `localllm` 하네스를 **호스트만 바꿔** 비교 — 로컬 `qwen2.5:32b-instruct-q4_K_M`(OpenCode+Ollama)
> vs `claude-opus-5`(Claude Code CLI, `claude -p`). 무인 스위트·oracle·결정론 게이트는 동일.
> 시나리오 S01·S03·S05·S06·S09·S10 × 2라운드, 구간 교대. 2026-08-11~12.

## 설계 — 호출 지점 한 곳만 교체

`cycle_driver` 의 호스트 호출 지점(`_opencode_run`)에 분기를 넣어 `HARNESS_DRIVER_HOST=claude-code`
면 `claude -p --permission-mode bypassPermissions --model <m>` 로 위임한다. 나머지 파이프라인
(7층 결정론 게이트·정규화 4종·판정 기록 검증·유계 재작업)은 **두 호스트가 공유**한다.

`claude -p` 에는 opencode 의 `--agent` 대응물이 없으므로, 로컬 구간이 폴백으로 쓰는 **주입 모드**
(역할 브리프를 프롬프트 앞에 붙임)로 고정해 프롬프트 형태를 맞췄다.

## 결과 1 — 호스트 격차

| 지표 | 로컬 32B | Claude Opus 5 |
|---|:-:|:-:|
| PASS | 9/12 (75%) | **12/12 (100%)** |
| **완주율** (expect_exit=0 인 S01·S05·S06) | **4/6 (67%)** | **6/6 (100%)** |
| 거짓 결과 (ACCURACY) | 0 | 0 |
| 총 소요 | 19분 | 24분 |

시나리오별로 갈린 지점이 분명하다 — 로컬이 실패한 **S05(엣지케이스)·S06(다중파일 import)·S09(리팩토링)**
를 Claude 는 4/4 통과했고, 게이트 지배 시나리오(S03·S10)는 양쪽 다 안정적이었다.

> **지표 정정**: 초기 보고에서 완주율을 "33% vs 100%" 로 적었는데 **오류**였다. `expect_exit` 를
> 확인하면 완주가 정답인 시나리오는 S01·S05·S06 뿐이다 — S10(치팅 차단)은 exit 2 가 **정상**이고
> S03·S09 는 양쪽 다 허용이다. 정상 정지를 실패로 세면 격차가 두 배로 부풀려진다.

## 결과 2 — 하네스는 강한 호스트를 붙잡고 있지 않았다

32B 우회책(경로 지시·탭 금지·`bash cat` 강제·전체 재작성 강제 등 측정 08 산물)을 문장 단위로
제거한 lean 프롬프트로 Claude 를 다시 돌렸다.

| 구간 | PASS | 완주 | 총 소요 |
|---|:-:|:-:|:-:|
| Claude 원본 프롬프트 | 12/12 | 6/6 | 24분 |
| **Claude lean** (우회책 제거) | 12/12 | 6/6 | **31분** |

품질은 완전히 동일한데 **lean 이 4/6 시나리오에서 느렸다** (총 +29%). 시나리오별: S01 +106s,
S06 +134s, S10 +151s 느려지고 S05 −65s, S09 −40s 빨라졌다.

⇒ **우회책은 핸디캡이 아니라 지름길이었다.** "파일을 통째로 재작성하라" 는 부분 편집 시행착오를
없애고, "`bash cat <파일들>` 로 읽어라" 는 탐색 단계를 건너뛰게 한다. 약한 모델의 결함을 막으려
만든 처방이 강한 모델의 **탐색 비용도** 줄이고 있었다. 표본이 시나리오당 2회라 +29% 를 단정할 수는
없지만, "우회책이 Claude 를 붙잡고 있다" 는 가설은 **지지되지 않는다**.

## 결과 3 — 측정 도구가 약한 호스트의 문체에 적합돼 있었다

이번 측정의 가장 큰 소득이다. 호스트를 바꾸자 **oracle 오탐 3종 7건 + 분류기 결함 1건**이 터졌고
전부 산출물을 직접 열어 반증했다. 네 건 모두 **내 것**이다.

| # | 결함 | 원인 | 로컬 159회에서 안 드러난 이유 |
|---|---|---|---|
| 1 | O7 반박문 오탐 | "criterion flagged as missing **is actually satisfied**" 의 `missing` 만 보고 결함 서술로 판정 | 32B 는 노트가 짧고 단정적 — 반박문을 쓰지 않는다 |
| 2 | O7 메타·기대동작 오탐 | "my earlier verdict was **wrong**"(자기 정정), "dividing by zero **fails** with ValueError"(정상 동작) | 동일 |
| 3 | O6 docstring 오탐 | 정규식이 `def f(x: float) -> float:` 의 **반환 어노테이션**을 못 넘음 | 32B 는 타입 힌트를 쓰지 않는다 |
| 4 | 분류기 INFO fallthrough | O7 을 INFO 로 강등하니 INFO 만 있는 기록이 "findings 없음" 분기를 못 타고 맨 아래 `else: BUG` 로 떨어짐 | 강등 자체가 이번에 한 수정이라 신규 |

**이대로 비교했다면 "Claude 가 거짓 결과를 8% 낸다" 는 정반대 결론**을 냈을 것이다. 말을 조리 있게
하는 호스트가 체계적으로 불리해지는 편향이었다.

### 수정
- **O6**: 정규식 → `ast` 파서. 어노테이션·데코레이터·다중행 시그니처에 무관. 4조합 검증 통과
- **O7**: 키워드로는 정밀도 회복 불가(관측 4/4 오탐 = 정밀도 0) → `ACCURACY` → **`INFO`(수동확인)** 강등.
  거짓 결과 탐지는 결정론 oracle(O2 ground truth / O3 최종판정 대조 / O4 환각파일 / O8 공허테스트)이 담당
- **분류기**: `INFO` 는 판정 비관여 (`findings_v` 로 분리)

O7 강등·O6 수정은 **오탐만 줄이므로** 기존 로컬 기준선(측정 08: ACCURACY 0/159)은 유효하다.

> **교훈**: oracle 은 검증 대상의 출력 분포에 조용히 적합된다. 159회를 통과한 측정기가 호스트를
> 바꾸는 것만으로 4건의 숨은 가정을 드러냈다. **측정기를 다른 대상에 한 번 대보는 것**이
> 표본을 늘리는 것보다 강한 검증이다.

## 결과 4 — Nemotron 3 Nano 30B 타진 (1~2단계)

`nemotron-3-nano:30b` (31.6B MoE, 활성 3.5B, Q4_K_M 24.3GB) 를 받아 재보았다. GPU 는 24GB.

| 항목 | nemotron `think=false` | nemotron `think=true` | qwen2.5:32b |
|---|:-:|:-:|:-:|
| 생성 속도 | **21.7 tok/s** | 23.6 tok/s | 16.7 tok/s |
| VRAM / CPU 오프로딩 | 19.7GB / **6.86GB (25%)** | — | 19.7GB / 1.5GB (7%) |
| 산출물 (동일 codegen 프롬프트) | 코드블록 3개, PASS·docstring ✅ | **코드블록 0개, PASS 누락** | 코드블록 2개, ✅ |
| thinking 소비 | 0자 | **1557자** (400토큰 예산을 추론에 소진) | — |

**속도는 qwen 보다 30% 빠르다** — 25% 오프로딩에도 MoE 활성 3.5B 이점이 살아 있다.

**단 `think=false` 가 필수 조건이다.** 첫 워밍업(16토큰)에서는 `response` 가 **빈 문자열**이고 내용
전부가 `thinking` 필드로 갔다(`done_reason: length`). 우리 드라이버는 `verify_loop record` 실행,
`VERDICT:` 한 줄, 항목형 `M1: met | 증거` 같은 **엄격한 형식**을 응답에서 파싱하므로, 추론이 예산을
먹으면 형식이 아예 나오지 않는다.

> **위 표는 Ollama 네이티브 `/api/generate` 경로 측정이다.** 하네스가 실제로 타는 경로는
> OpenAI 호환 `/v1/chat/completions` 이고, 거기서는 결과가 달랐다 — `think=false` 는 **무시되지만**
> 추론이 `reasoning` 필드로 **분리**되어 `content` 는 깨끗하다 (결과 6). 즉 파서 오염 위험은 해소됐고
> 남은 위험은 토큰 예산 잠식이다. `reasoning_effort=none` 은 추론을 끄지만 답 품질이 나빠졌다
> (자명한 과제에 `fail` + 산문).

## 결과 5 — localllm 완주율 개선 시도: 1건 채택, 2건 철회

완주 실패 3분류 중 **하네스가 고칠 수 있는** S09(동일 진단 반복)를 겨냥해 3건을 만들고,
S09 집중 A/B(구간당 6 사이클)로 재봤다. 지표는 통과/실패 비율이 아니라 **grader PASS 까지의
재작업 횟수** — 앞선 측정에서 비율은 분산에 묻힌다는 것이 확인됐기 때문이다.

| 지표 | 개선 전 | 개선 후 |
|---|:-:|:-:|
| grader 통과 | 3/6 | 4/6 |
| 통과 시 재작업 횟수 | 1.3회 | 1.2회 |
| 평균 소요 | 152s | 147s |
| require 위반 발생 | 6/6 | 6/6 |
| 지목수리 발동 / salvage 발동 | 0 / 0 | 2 / 0 |

**효과는 검증되지 않았다.** 3/6 → 4/6, 1.3 → 1.2회는 n=6 에서 노이즈다.

> **중간 관측의 함정**: n=1 시점에는 극적인 대비(개선 전 3회 실패 → 개선 후 1회 통과)로 보였다.
> 6라운드를 채우니 베이스라인도 r2·r3·r5 에서 1~2회로 통과했다. **단일 라운드 관찰은 오해를 부른다.**

### 채택 결정 (ADR-019 규율을 내 개선에도 적용)

| 변경 | 결정 | 근거 |
|---|---|---|
| require 위반을 PROBLEMS DETECTED 목록에 포함 | **유지** | 효과 미검증이나 **논리적으로 옳은 버그 수정** — 위반이 "고쳐야 할 문제" 목록에서 빠져 테스트 출력 블롭에 묻혀 있었다. 비용·위험 0 |
| 코드블록 salvage | **철회** | 12 사이클 0회 발동. 유일한 발동(S06)에서도 응답에 코드블록이 없어 구제 실패 — 가정("내용은 만들었는데 쓰기만 실패")이 실제 실패 양상과 어긋난다 |
| 지목형 수리 + 파일 생성 3회 | **철회** | 2회 발동으로는 판단 불가. 근거 없는 코드를 남기면 다음 사람이 검증된 개선으로 오해한다 |

⇒ 순 변경 9줄(주석 포함). 되돌리는 중 `tries` 제거 후 `len(tries)` 참조가 남아 런타임
NameError 가 될 상태였던 것을 커밋 전에 잡았다.

### 고칠 수 없는 실패도 있다
S01·S06 은 unittest 가 `OK` 만 출력해 기대 토큰 `PASS` 를 못 맞추는 유형이다. 기존 처방
(unittest 금지 + 코드 템플릿)이 **이미 발동한 뒤에도** 3회 실패했다 — 처방이 없어서가 아니라
처방을 따르지 못해서다. 하네스는 정확히 검출하고 정직하게 에스컬레이션했다.
**모든 실패를 하네스가 고쳐야 하는 것은 아니다.**

## 결과 6 — Nemotron 3 Nano 30B: 도구 호출 관문에서 탈락 (보류)

> ⚠️ **이 절의 모델 판정은 결과 8 에서 정정됐다** — 생짜 `opencode run` 스모크였고 qwen 대조군도
> 같은 조건에서 멈췄다. 도구 호출 자체는 하네스 경로에서 동작한다.

| 관문 | 결과 |
|---|---|
| 레지스트리·전역 등재·모델 해석 | ✅ `ollama/nemotron-3-nano:30b` |
| 생성 속도 | ✅ 21.7 tok/s (qwen 16.7 대비 +30%) |
| 추론 트레이스 오염 | ✅ OpenAI 호환 레이어가 `reasoning` 필드로 분리 — `content` 안전 |
| VRAM | ⚠️ 26.55GB 중 **6.86GB(25%) CPU 오프로딩** (GPU 24GB) |
| 추론의 토큰 예산 잠식 | ⚠️ `max_tokens=32` 면 content 가 **빈 채로 잘림**(`finish=length`) |
| **도구 호출** | ❌ **2/2 실패** |

- **1차**: `edit` 스키마 위반 — `oldString` 키 누락(신규 파일은 `""` 로 호출해야 함). 오류 2회 후
  파일 생성 실패, 마지막엔 *"Please provide the three items above ... and I'll issue a proper edit call"*
  로 **사람에게 되물었다**. 139초, 산출물 0
- **2차**: `oldString: ""` 규약과 "묻지 말라"를 명시 → 스키마 오류 0회이나 **400초 타임아웃**, 산출물 0

⇒ **보류.** 속도·형식 지표는 좋지만 `cycle_driver` 전체가 "모델이 edit/bash 로 산출물을 만든다"는
전제 위에 서 있다. **산출물 0 인 모델에게 생성 속도는 무의미하다.** 측정 04 가 14B 를 탈락시킨 것과
같은 관문이고 원인은 다르다 — 14B 는 도구를 안 쓰고 설명했고, nemotron 은 도구를 쓰려 하지만
규약을 못 맞추고 되묻거나 배회한다.

두 번의 시도에서 오류 양상이 **개선이 아니라 이동**했으므로(스키마 위반 → 타임아웃) 프롬프트
교정의 방향이 보이지 않는다. 전용 분기를 넣으려면 효과를 먼저 재야 하는데 재려면 분기를 먼저
만들어야 하는 순환이라, 근거 없이 코드를 늘리지 않는다.

> 남은 각도: **판정(judge) 전용** 사용. 판정은 파일을 만들지 않고 `bash` 로 읽고 record 만 하므로
> 도구 부담이 가볍고 `content` 분리도 확인됐다. 다만 `bash` 호출은 여전히 필요하고 토큰 예산
> 잠식 위험이 남는다. 전역 설정 등재는 유지하되(재타진 편의) 역할 매핑에는 넣지 않았다.

## 결과 7 — Gemma 4 26B 도 도구 호출 관문 탈락 / "OpenCode 는 qwen 전용" 가설 기각

> ⚠️ **"도구 호출 탈락" 판정은 결과 8 에서 정정됐다** (400초 타임아웃은 모델 호출 전 정지).
> 단 하네스 경로 재검증에서 26B 는 별개 사유로 실패했다. "qwen 전용" 기각은 유효하다.

nemotron 보류 후 동급 대안으로 `gemma4:26b`(25.8B MoE, Q4 18.0GB)를 재보았다.

| 관문 | gemma4:26b |
|---|---|
| VRAM | ✅ **오프로딩 0%** (17.35GB 전량 GPU — nemotron 25% 오프로딩과 대조) |
| 생성 속도 | ✅ **107.5 tok/s** — qwen(16.7)의 **6.4배**, nemotron(21.7)의 5배 |
| 직접 API | ✅ 네이티브·OpenAI 호환 모두 정상, 코드 생성 깔끔 |
| **OpenCode 도구 호출** | ❌ **400초 타임아웃, 출력 0바이트** |

`gemma4:12b` 도 동일 양상(0바이트 타임아웃)이었다. 반면 직접 API 에서는 26B 가 정상 동작하므로
**모델 고장이 아니라 OpenCode 경로 특유의 실패**다.

> 유보: `"OK"` 두 글자에 completion_tokens 53 을 쓴다(추론 필드 0인데도). 서두 오버헤드가 커서
> `max_tokens` 가 작으면 content 가 빈 채로 돌아온다 — `num_predict=24` 에서 빈 응답, 200 에서 정상.

### "OpenCode 가 qwen 전용" 가설 — 기각

| 검증 | 결과 |
|---|---|
| 바이너리 내 모델명 언급 | qwen 3회 < **gemma 5회** < mistral 10 < llama 15 — 특수 처리 흔적 없음 |
| 모델 레지스트리(`~/.cache/opencode/models.json`) | **183 provider** 등재. nemotron 계열도 `tool_call=True` 로 정식 등재 |
| Ollama 능력 선언(`/api/show`) | **전 후보가 `tools` 선언** (gemma4:26b = `completion,vision,tools,thinking`) |

OpenCode·Ollama 어느 쪽도 특정 계열을 배제하지 않는다. 실패는 **모델이 OpenCode 가 주입하는 도구

> 다만 레지스트리에 `ollama` provider 는 **비어 있다**(사용자 정의 provider 라 능력 정보 없음).
> OpenCode 가 능력을 추정하지 못한 채 도구를 주입하는 것이 실패에 관여했을 수 있으나,
> 같은 조건에서 qwen 이 동작하므로 단독 원인은 아니다.

### 절차 교훈 — 관문 순서를 잘못 잡았다
nemotron·gemma 모두 **VRAM·속도·형식을 통과시키고 마지막 도구 호출에서 탈락**했다. 24GB·18GB 를

⇒ 이번 타진의 소득: **속도 병목의 답은 찾았다**(오프로딩 없는 MoE = 6.4배). 다만 그 속도를 우리

## 결과 10 — Gemma·Nemotron 도구 호출 실패의 진짜 원인: 추론 예산 잠식

결과 8 이 모델 판정을 전수 무효화한 뒤, 원시 API 에 스트리밍 프로브를 붙여 **도구 호출 델타가
언제 나오는지**를 직접 관측했다. 원인이 나왔다 — 모델 결함이 아니라 **우리 파이프라인의 예산 설정**이다.

### 관측

`gemma4:26b`, 스트리밍 + `tools=[edit]`, 프롬프트 "hello.py 를 만들어라":

| `max_tokens` | 델타 키 분포 | reasoning | content | tool_calls | finish |
|---|---|---|---|---|---|
| 400 | `role:386 content:386 reasoning:385` | 1521자 | 0자 | **0** | **`length`** |
| 2000 | `role:546 content:546 reasoning:544 tool_calls:1` | 2018자 | 0자 | **1** | **`tool_calls`** |

같은 조건의 `qwen2.5:32b`: **청크 2개**, tool_call 델타 1개, 이름 `['edit']`, `finish=tool_calls`.

### 해석

gemma 는 도구를 호출하기 **전에** 추론을 약 2000자(≈500토큰) 쓴다. 예산이 그보다 작으면 추론
중간에서 잘리고, 도구 호출 델타는 **아예 생성되지 않는다**. `finish=length` 가 그 증거다.

추론 내용 자체는 정확했다:

> "The user wants to create a file named `hello.py` … I should use the `edit` tool for this."

**모델은 무엇을 해야 하는지 알고 있었고, 말할 지면이 없었다.** 비스트리밍 프로브에서 gemma 가
성공한 것도 이제 설명된다 — 그때는 예산이 넉넉했다.

### 두 모델의 실패가 같은 뿌리였다

Ollama 능력 선언이 셋을 정확히 갈라놓는다:

| 모델 | 능력 선언 | 추론 모델 | 도구 호출 전 지출 |
|---|---|---|---|
| `qwen2.5:32b` | `completion, tools` | ❌ | 없음 (즉시 호출) |
| `gemma4:26b` | `completion, vision, tools, **thinking**` | ✅ | ≈500토큰 |
| `nemotron-3-nano:30b` | `completion, tools, **thinking**` | ✅ | (동종 — `max_tokens=32` 에서 content 공백 절단 관측) |

결과 6·7 이 "도구 호출 관문 탈락"으로 판정한 두 모델은 **둘 다 추론 모델**이었고, 통과한 유일한
모델은 **추론 모델이 아닌** qwen2.5 였다. 우리 하네스가 "qwen 에서만 동작"한 것은 모델 편애가
아니라 **추론 예산을 고려하지 않은 파이프라인**에 추론 모델을 넣었기 때문이다.

### 대응

전역 OpenCode 설정에 모델별 출력 예산을 명시한다 (스키마 확인된 필드):

```jsonc
"gemma4:26b":           { "limit": { "output": 4096 } },
"nemotron-3-nano:30b":  { "limit": { "output": 4096 } }
```

### 남는 유보

- 예산을 올리면 **도구 호출마다 추론 500토큰**이 붙는다. gemma 의 107 tok/s 가 이 오버헤드를
  상쇄하는지는 별도 측정이 필요하다.
- 판정 단계에서 `VERDICT: pass` 13자를 얻으려 추론 500토큰을 쓰는 비효율은 그대로 남는다.
- 이 대응이 **하네스 경로에서** 완주로 이어지는지는 아직 미검증이다 (아래 결과 11).

### 방법론 교훈

결과 8 의 교훈("모델을 탓하기 전에 관문 도달을 증명하라")에 한 겹이 더 붙는다 —
**모델의 실패를 관측할 때는 모델이 말할 수 있었던 분량을 함께 기록하라.** `finish` 사유
한 필드가 "모델이 못 했다"와 "우리가 지면을 안 줬다"를 가른다.

## 결과 11 — localllm.nem (nemotron) 1차 A/B: 예산 관문은 통과, 완주는 부모가 우세

결과 10 의 처방(`limit.output` 등재)을 적용해 `localllm.nem` 변형을 만들고, 부모 `localllm`
(qwen2.5) 과 같은 시나리오로 비교했다.

### 조건

| 항목 | 값 |
|---|---|
| 시나리오 | S01(단일 파일) · S06(다중 파일 import 체인) |
| 라운드 | 각 1회 |
| 부모 구간 | `localllm` — qwen2.5 14B/32B 2 티어 |
| 시험 구간 | `localllm.nem` — `nemotron-3-nano:30b` 단일, `limit{context:32768, output:4096}` |
| 대조군 | 부모 구간이 곧 대조군 (같은 배치) |

### 결과

| 구간 | S01 | S06 | PASS | 총 소요 |
|---|---|---|---|---|
| qwen (부모) | **PASS** exit0 144s | MODEL exit2 118s | **1/2** | 263s |
| nemotron (.nem) | MODEL exit2 460s | MODEL exit2 1495s | **0/2** | 1956s |

부모가 기존 실측과 일관되게 동작했으므로(S01 통과, S06 은 알려진 난이도) **배치는 유효**하다.

### 확인된 것 — 예산 관문은 통과했다

S06 에서 nemotron 이 **`greet.py` 를 실제로 생성했다** (시도 2/2 에서 `✓ 확인`). 이것이 결정적이다:
결과 6 에서 nemotron 을 "도구 호출 관문 탈락"으로 판정했던 상태에서는 파일이 **하나도** 생기지
않았다. 예산을 준 뒤 도구 호출이 성립했다 — **결과 10 의 처방은 유효하다.**

### 확인된 것 — 그러나 완주는 부모가 낫다

| 지표 | qwen (부모) | nemotron (.nem) |
|---|---|---|
| 대상 파일 생성 성공 | **3/4** | **1/4** |
| 완주(PASS) | 1/2 | 0/2 |
| 벽시계 | 263s | **1956s (7.4×)** |

실패 양상도 다르다. 부모의 S06 실패는 파일 하나(`greet.py`)를 못 만든 것이고, nemotron 은
S01 의 단일 파일조차 2 회 시도에서 못 만들었다. 게이트는 두 경우 모두 **모델 보고와 무관하게
파일시스템 기준**으로 검출했다 — 하네스는 정확히 동작했다.

### 교란 요인 (해석의 한계)

1. **프롬프트가 qwen 에 맞춰져 있다.** 측정 11 결과 3 이 이미 기록한 문제 — 지금의 프롬프트는
   부모 구간을 완주시키려고 32B 에 맞춰 다듬은 것이다. nemotron 은 남의 옷을 입고 평가받았다.
2. **표본 1 라운드 × 2 시나리오.** 측정 09 가 확인한 대로 이 스위트의 판정 분산은 크다.
   이 수치로 "nemotron 이 열등하다"고 결론짓기에는 부족하다.
3. **예산 4096 이 충분한지 미확인.** 파일 내용도 출력 토큰이다. 추론 2000 토큰을 쓴 뒤
   파일 본문을 쓰려면 남는 지면이 좁다 — 예산 자체가 실패 원인일 수 있다 (결과 12 에서 검증).

### 판정

이 시점에서 정직한 결론은 하나뿐이다: **`localllm.nem` 은 동작하는 변형이지만, 부모를 대체할
근거는 없다.** 예산 관문 통과는 확인됐고, 완주율 우위는 확인되지 않았다. 부모 `localllm` 을
qwen 기준으로 불변 유지한 ADR-021 결정 1 이 이 결과로 정당화된다 — 부모를 갈아끼웠다면
비교 대상이 사라졌을 것이다.

## 결과 12 — 예산 가설 기각: 4096 은 충분했고, 남은 격차는 예산이 아니다

결과 11 이 남긴 유보 3번(예산 4096 이 파일 쓰기에 충분한가)을 직접 시험했다. 파일 내용도 출력
토큰이므로, 추론이 2000 토큰을 쓴 뒤 본문을 쓸 지면이 모자랄 수 있다는 가설이었다.

### 조건

`nemotron-3-nano:30b` 의 `limit.output` 만 **4096 → 16384** 로 올리고 S01 을 재실행했다.
같은 배치에 부모(qwen) 대조군을 넣었다.

### 결과

| 구간 | 판정 | 소요 | 생성된 파일 |
|---|---|---|---|
| qwen (4096 배치) | **PASS** | 144s | `word_count.py` + `test_word_count.py` |
| nemotron `output=4096` | MODEL | 460s | `word_count.py` 만 |
| nemotron `output=16384` | MODEL | **768s** | `word_count.py` 만 |
| qwen (대조, 같은 배치) | MODEL | 94s | `word_count.py` + `test_word_count.py` |

### 판정 — 가설 기각

예산을 4 배로 올렸는데 **산출물이 동일하다**. 두 경우 모두 구현 파일은 만들고 테스트 파일은
만들지 못했다. 바뀐 것은 **소요 시간뿐**이다 — 460s → 768s (**67% 증가**).

예산을 주면 nemotron 은 그만큼 더 추론하고, 그 추론이 결과를 바꾸지 않는다. 따라서:

- **`limit.output=4096` 은 충분하다.** 변형 기본값을 유지한다 (상향은 순손실).
- **남은 격차는 예산이 아니라 지시 이행이다.** "구현 파일 + 테스트 파일" 두 개를 만들라는
  과제에서 두 번째 파일을 빠뜨린다. 결과 10 이 연 관문 뒤에 **다른 관문**이 있었다.

### 대조군에 대한 정직한 처리

이 배치의 qwen 대조군도 **MODEL 로 실패했다** (unittest 가 `OK` 만 출력해 기대 토큰 `PASS`
미충족 — 측정 11 결과 5 가 이미 "모델 한계"로 분류한 알려진 양상). 판정 계열이 INFRA 가 아니라
MODEL 이므로 **환경·설정은 건강했다** — 대조군 규율이 겨냥하는 실패(환경·설정)는 아니었다.

다만 이것이 **부수적으로 드러낸 사실**이 하나 있다: 같은 qwen 이 같은 S01 에서 한 번은
PASS(144s), 한 번은 MODEL(94s) 이었다. **S01 은 부모에게도 결정론적이지 않다.** 측정 09 가
기록한 판정 분산이 시나리오 통과 여부에서도 나타난다 — 결과 11 의 "1/2 대 0/2" 를 격차의
크기로 읽으면 안 된다는 뜻이다.

### 남은 것

nemotron 의 다중 파일 지시 이행을 개선할 수 있는지는 **프롬프트 적합성** 문제로 넘어간다
(결과 11 교란 요인 1 — 지금 프롬프트는 qwen 에 맞춰 다듬어져 있다). `.claude/policy/` 로
다룰 수 있는 표면이고, autoresearch 가 자동 탐색할 수 있는 표면이기도 하다. 이번 F030 의
범위는 여기까지다 — **변형은 동작하고, 우위는 주장하지 않는다.**

## 결과 13 — 근본원인: 하네스가 만족 불가능한 도구 지시를 하고 있었다

결과 12 가 남긴 질문("남은 격차는 지시 이행")을 프록시로 원시 트래픽을 잡아 추적했다.
원인은 모델이 아니라 **하네스의 지시문**이었다.

### 캡처 (스트리밍 프록시, qwen 대조군 동일 배치 통과로 프록시 건강 확인)

같은 과제 — `word_count.py` 를 만들어라:

| 구간 | 호출한 도구 | 인자 | 결과 |
|---|---|---|---|
| qwen2.5:32b | **`write`** | `{filePath, content}` | ✅ 파일 생성 (30s) |
| nemotron-3-nano:30b | **`edit`** | `{filePath, content}` | ❌ 파일 없음 (111s) |

두 모델 모두 도구를 **정확히 1회** 호출했고 인자 JSON 도 유효했다. `finish_reason` 도
둘 다 `tool_calls` 였다. 차이는 **어느 도구를 불렀는가** 하나뿐이다.

### OpenCode 도구 스키마 (요청 페이로드에서 실측)

| 도구 | required |
|---|---|
| `edit` | `filePath`, **`oldString`**, **`newString`** |
| `write` | `filePath`, **`content`** |

### 하네스가 준 지시

```
Call the edit tool with filePath exactly "word_count.py" ... and the complete file content.
```

`edit` 에는 `content` 파라미터가 **없다**. 이 지시는 스키마상 **만족 불가능**하다.

- **qwen 은 지시를 무시**하고 `write` 를 불렀다 → 통과
- **nemotron 은 지시를 그대로 따랐다** → `edit(filePath, content)` → 필수 인자 2개 누락 → 실패

즉 **하네스가 순종적인 모델에게 벌을 주고 있었다.** 결과 11·12 가 "nemotron 의 다중 파일
지시 이행 격차"로 분류한 것은 모델의 결함이 아니라 우리 프롬프트의 결함이었다.

### 왜 오래 숨어 있었나

부모 변형은 qwen 으로만 검증됐고, qwen 이 **틀린 지시를 교정해 주었기 때문에** 스위트가
통과했다. 통과하는 파이프라인은 재검사되지 않는다. 모델을 바꾸자마자 드러났다 —
**모델 축 분기(ADR-021)가 없었다면 이 버그는 계속 숨어 있었을 것이다.**

### 수정

`cycle_driver` 의 두 지점(역할 프롬프트 TOOL RULES / `_ensure_files` 파일 생성 지시)을
`write` 기준으로 바로잡고, `edit` 는 "기존 파일 수정용이며 파일을 만들 수 없다"고 명시했다.
**localllm · localllm.nem · localllm.aif 세 변형에 모두 적용** — 모델 무관 결함이다.

### 계측 결함 4건 (이번 조사에서 내가 만든 착시)

원인을 찾기까지 **내 프로브가 만들어낸 가짜 관측**을 네 번 걷어내야 했다. 기록해 둔다:

| 결함 | 만들어낸 착시 | 수정 |
|---|---|---|
| 샌드박스를 템플릿 트리 안에 배치 | rsync 재귀 중첩 → 이후 모든 복사 exit 23 | `run_suite.py` 가드 |
| `limit` 에 `output` 만 등재 | OpenCode 가 전 실행 거부 → "환경 정지" 오진 (배치 2개 폐기) | `context` 동반 필수 |
| 프록시 단일 스레드 | 동시 요청 직렬화 → 타임아웃 | `ThreadingHTTPServer` |
| 응답 로그 20000자 절단 | `finish=None`, `tool_calls=0` → **모델이 도구를 안 불렀다고 오판** | 요약을 로그 시점 계산 |
| 프록시가 `up.read()` 로 전체 버퍼링 | SSE 정지 → 클라이언트 빈 응답 | 청크 단위 스트리밍 전달 |

넷째가 가장 위험했다 — **모델이 한 일을 안 했다고 보고하게 만들었다.** 그래서 요약(델타
분포·길이·`tool_calls`·`finish_reason`)을 로그 시점에 계산하도록 바꿨다. 본문이 잘려도
판정 근거는 살아남는다.

교훈: **대조군은 모델뿐 아니라 계측 도구에도 필요하다.** 프록시를 고친 뒤 qwen 을 먼저
통과시켜 프록시 자체의 건강을 증명하고 나서야 nemotron 판정을 신뢰했다.

### 수정 효과 실측 (같은 과제 반복)

지시문을 `write` 기준으로 고친 뒤 같은 과제를 반복했다:

| 구간 | 성공 | 소요 |
|---|---|---|
| **nemotron (수정 후)** | **5/5** | 104 · 123 · 150 · 118 · 158s |
| qwen 대조군 | 1/2 | 30s / 11초 빈 응답 실패 |

수정 전후를 합치면 nemotron 은 **7회 중 6회 성공**이다. 수정 전에는 `edit` 를 불러
일관되게 실패했다. 산출물도 정확했다 — `len(s.split())` + docstring.

두 가지를 덧붙여 둔다:

1. **표본 2개로 "간헐적"이라 판단했던 것은 틀렸다.** 수정 직후 1회 실패해 간헐성을 의심했지만,
   5회를 더 돌리자 전부 성공했다. 그 1회는 아래 qwen-2 와 같은 **호스트 간헐 실패**로 보인다.
2. **qwen 대조군도 1건 실패했다** (11초, 빈 응답). 측정 08 이 기록한 호스트 간헐 실패의 알려진
   양상이고 모델 무관이다. 이 환경에서 단발 실패 1건으로 모델을 판정하면 안 된다는 근거가 하나 더 늘었다.

### 결과 11·12 에 대한 소급 정정

결과 11 의 "완주는 부모가 우세(1/2 대 0/2)"와 결과 12 의 "남은 격차는 다중 파일 지시 이행"은
**이 결함 위에서 얻은 수치**다. nemotron 은 지시대로 `edit` 를 불렀고 그래서 파일이 생기지
않았다 — 모델의 능력이 아니라 우리 지시가 만든 실패다. 두 결과의 수치는 **무효**이고,
수정 후 스위트로 다시 측정해야 한다.

결과 12 의 "예산 4096 은 충분하다"(16384 로 올려도 산출물 동일)는 **여전히 유효**하다 —
그 실험은 두 구간 모두 같은 잘못된 지시를 받았으므로 예산 비교로서는 성립한다.
